# 配置図と位置情報によるパネルの自動特定（設計案）

- 状態: **設計案（未承認）。承認されるまで実装しない**
- 作成: 2026-11-06（ユーザー指示: グリッドを画像ごとに人が描く方式から、配置と位置情報で画像内のパネルを自動で特定する方式へ切り替える）
- 中止したもの: 1 枚に複数のグリッドを自動提案する改善、最初の 5 枚でのグリッド入力の時間計測
- 残すもの: 手動のグリッド入力（自動で特定できなかった画像の予備）
- 前提: 設計原則（[IMPROVEMENT_PLAN.md](IMPROVEMENT_PLAN.md) セクション 1）。オルソモザイクは作らない（原則 12）
- この文書には、顧客の画像・座標・シリアル番号と SDK の評価結果を書かない

## 0. 全体の流れ

```
[発電所ごとに 1 回]
  配置の登録 ── 図面の座標から ／ 画像から作った「架台の地図」を人が確認
       │        架台（段数・列数・向き・位置）→ パネル番号を自動で振る
       ▼
[点検ごと・画像ごと（自動）]
  ① 画像の位置（RTK・高度・LRF・向き）→ 画像と地上の座標の対応（georef）
  ② 近くの架台を画像に投影（予測の位置）
  ③ 画像の中の架台の端を検出して、投影の位置を補正（位置合わせ）
  ④ ずれ（残差）を記録。閾値以内 → パネル領域（今の panel_grids と同じ形）を自動で作る
                        閾値超え・架台が見つからない → 要確認（手動グリッドの画面に投影結果を下書きとして出す）
  ⑤ 今の解析エンジン・ルール判定で異常を検出・分類（判定の仕組みは変えない）
       ▼
[点検ごと（自動）]
  ⑥ 異常を地上の位置（パネル＋パネル内の位置）でまとめる。「N 枚中 M 枚で高温」を記録
       ▼
[人]
  ⑦ まとめた異常の候補だけを確認する（代表の画像＋同じ場所を写した他の画像を並べて見る）
```

**原則との関係**

| 原則 | この設計での扱い |
|---|---|
| 位置の対応が取れないものを正常にしない | 位置合わせできなかった画像は `needs_review`（理由: 位置合わせ不可）。どの画像でも解析できなかったパネルは「未確認」とし、正常にも点検済みにもしない（`last_inspected_at` を更新しない） |
| パネルへの割り当ては位置情報か人の指定に限る | 異常のパネルは「位置合わせ後の画像上の位置 → 登録した配置」で決める（位置情報）。位置合わせに失敗した画像は人がグリッドを指定する（人の指定）。並び順による割り当てはしない |
| 判定は温度データとルール | 検出・分類・重大度は今のルール判定のまま。位置合わせは「どの画素がどのパネルか」を決めるだけ |
| 閾値をハードコードしない | 位置合わせの閾値は新しい設定ファイル（`config/layout_overlay.yml`）に置く。画像ごとに使った値と設定の版を記録する |
| 確定済み（locked）を書き換えない | 配置の登録し直しや再解析で、確定済みの異常の重大度・判断は変えない（Phase 5b の割り当て直しの一覧と同じ扱い） |

パネル番号を規則で振る（A の 3）のは「実在するパネルの名前の付け方」であり、異常の割り当てではない。異常をどのパネルに付けるかは常に位置で決める。

## A. 配置の登録方法

### A-1. 登録するもの（データモデル案）

**`pv_blocks`（架台。新規）**

| カラム | 型 | 説明 |
|---|---|---|
| site_id | references | |
| label | string | 架台の名前（例 `A03`）。自動で振り、人が変えられる |
| corners_local | jsonb | 4 隅の地上の座標（発電所の原点からの東・北 m）。パネル面を真上から見た形 |
| azimuth_deg | decimal | 架台の長辺の向き |
| rows / cols | integer | 段数・列数（例: 2 段 × 10 列） |
| panel_orientation | string | `portrait` / `landscape` |
| tilt_deg | decimal, null 可 | 傾斜角（図面にあれば。無ければ画像から推定した値と、その出どころ） |
| surface_elevation_m | decimal, null 可 | パネル面の標高（LRF の当たった位置の標高から推定。位置の変換に使う） |
| source | string | `drawing`（図面の座標）/ `image_map`（画像から作った地図）/ `manual`（人が追加・修正） |
| status | string | `proposed`（候補）/ `confirmed`（人が確認済み） |
| evidence | jsonb | 画像から作った場合: 何枚の画像で検出したか、位置のばらつき（m） |

- `sites` に `geo_origin_lat` / `geo_origin_lng`（発電所の原点）、`layout_confirmed_at` を追加
- `panels` に `pv_block_id`・`block_row`・`block_col` を追加。既存の `gps_lat` / `gps_lng` には架台から計算したパネル中心を入れる。ダッシュボードの `position_x` / `position_y` は地上の座標から作る
- 座標は発電所の原点からの平面（東・北 m）で計算する（範囲が数百 m なので平面で十分）

### A-2. 図面に座標がある場合

1. 図面（CAD など）から、架台ごとに「4 隅の緯度経度（または中心＋向き＋大きさ）・段数・列数」を CSV にする（雛形を用意。作るのは人または図面の作成元）
2. CSV を取り込み、架台とパネルを登録する（確認画面 → 確定。Phase 5b と同じ「全部の置き換え」）
3. **最初の点検で全体の合わせ込みを 1 回行う**: 図面の座標と画像（RTK）の座標系の違い（測地系・図面の作成精度）で、全体が数十 cm〜1 m 程度ずれることがある。画像から検出した架台と図面の架台を突き合わせ、全体の平行移動（必要なら回転）を 1 回だけ求めて、ずれの大きさを確認画面に出す。人が確認して確定する
4. 平面直角座標（図面でよく使う）は、最初は「緯度経度に変換した CSV」を受け付ける形にする。平面直角座標のまま取り込む変換は後で追加

### A-3. 図面に座標が無い場合: 画像から「架台の地図」を自動で作る

**可能と考える。** 同じパネルが 10 枚以上の画像に写るエリア撮影なので、架台は多くの画像に丸ごと写る。

1. 点検の画像（選んだもの、または全部）で架台を検出する（温度のばらつきが小さい長方形。手順 7 の試作 2 を改良し、架台の端を画素単位で合わせ込む）
2. 検出した架台を、画像ごとの位置の変換（B-1）で地上の座標に移す
3. 地上で近いもの同士（例: 中心が 3 m 以内・向きが近い）を同じ架台としてまとめ、4 隅の位置を中央値で決める。各架台について「何枚の画像で見つかったか」「位置のばらつき」を残す
4. 段数・列数は、架台の大きさとパネルの大きさ（発電所に登録するモジュールの寸法）、架台の中のパネルの境目の線の間隔から推定する
5. **人が一度だけ確認・修正する**（発電所ごとに 1 回）
   - 画面: 架台の地図（四角の配置図）と、架台をクリックするとその架台が写った画像に投影を重ねたものを並べて表示
   - 操作: 架台の追加・削除・分割・結合、段数・列数の修正、向きの微調整、ラベルの変更
   - 自信の低い架台（見つかった枚数が少ない・ばらつきが大きい・大きさが周りと違う）を先に並べ、確認の順番を絞る
   - 人の作業の見込み: 架台 1 つあたり 5〜10 秒（正しいものは一覧で流し見）＋修正が要るものに 30 秒〜1 分。架台 200 個の発電所で **30〜60 分程度（1 回だけ）**
6. 確定したら `confirmed`。2 回目以降の点検は、この地図をそのまま使う（補正は画像ごとに自動）

**実装（2026-11-07、手順 4 の解析エンジンの部分）**: `python -m analyzer build-block-map`（`analyzer/layout/`）。検証で分かったことを入れた:
- パネル面の標高は LRF がパネルに当たった画像の `LRFTargetAbsAlt` から。パネルの上端・下端は ±δ の高さで地上に移す
- 画素の角度の倍率は短辺（δ に左右されない）で、δ は長辺で、それぞれ「その画像を除いた地図」とのずれが最小の値を探す（両方を同時に探すと、長辺では効き方がほぼ同じで決まらなかった）
- 架台の端は、長辺から求めた列の中心に割り当ててからまとめる（列に直交する位置だけでまとめると、通路の誤検出を介して隣の列の端とつながった）
- 架台の長さは端どうしの間隔の分布の山から決める（誤検出の短い間隔で中央値が下がったため）
- **Rails 側（2026-11-08）**: 点検の画面の「架台の地図の候補を作る」（モジュールの幅・長さ・段数の既定値・パネルの向く方位を入力）→ `BuildBlockMapJob` が位置合わせに使える画像だけで `build-block-map` を呼び、`block_map_proposals` に保存 → 候補の画面（配置図・推定値・ずれ）→ CSV をダウンロードして直すか、「この候補で登録の確認へ」で架台の登録の確認画面に進む（確定するまで登録しない）。地図の確認画面（追加・削除・分割の操作）は作っておらず、修正は CSV で行う

注意点:
- この地図は画像の座標系で作るので、画像との合い方は良い。一方、図面の番号（顧客の番号）とは無関係なので、顧客の番号で報告するには A-5 の対応付けが要る
- 撮影範囲の端の架台は、丸ごと写る画像が少なく、見つからないことがある（確認画面で追加する）
- 草・通路・建物が長方形に見えて架台と間違えることがある（確認画面で削除する）

### A-4. パネル番号を自動で振る

- 架台のラベル: 架台の向きに沿って「列（アレイの行）」にまとめ、列は北から南へ A・B・C…、列の中は西から東へ 01・02…（例 `B07`）。始点の角と向きは発電所ごとに選べるようにする（図面の番号の付け方に合わせるため）
- パネル番号: `架台ラベル-段-列`（例 `B07-1-04`。段は上から、列は西から）。これも始点の角を選べる
- 番号は配置の確定時に一度だけ振り、点検ごとに振り直さない（パネルの記録が続くように）

**実装（2026-11-07、手順 3）**: 架台の CSV の列（ユーザー承認）は、架台ラベル（空欄なら自動）・段数・列数・4 隅の緯度経度（順不同）と、任意のパネルの向き・パネルの向く方位（既定 180）・傾斜角・上端と下端の標高・出どころ。書き出し用の「確認が必要」「観測の数」は取り込みで無視する。画面は発電所一覧の「架台を登録」→ CSV → 確認画面（配置図）→ 確定。登録済みの架台は CSV で書き出せる（同じ形で取り込み直せる）。`pv_blocks`・`sites.geo_origin_lat/lng`・`panels.pv_block_id/block_row/block_col` を追加。パネルの置き換えは `PanelLayoutImport` をそのまま使う

### A-5. 今の配置図 CSV（Phase 5b）との関係

- **パネルの登録・置き換えの仕組みは Phase 5b のものを使う**（確認画面、全部の置き換え、消えるパネルに付いた異常は紐付けを外して割り当て直しの一覧へ、locked は変えない）。架台の登録から作ったパネル一覧を、同じ置き換えの処理に渡す
- Phase 5b の CSV に全パネルの緯度経度（`gps_lat` / `gps_lng`）がある場合は、それを「図面に座標がある場合」の入力として使える（パネルの位置から架台をまとめる）
- 図面の番号・ストリング番号・パワコン番号を使いたい場合: 画像から作った地図で確定した後に、Phase 5b の CSV（パネル番号と位置）で番号とストリングの情報を上書きする対応付けを用意する（位置の近いパネル同士を対応させ、対応しないものは一覧に出して人が決める）
- `start_panel_ref` は、手動のグリッドでも使う（位置合わせに失敗した画像で、人がグリッドを置くと、下書きの投影から架台のパネル番号が入る）

## B. 画像と配置の対応

### B-1. 画像と地上の座標の対応（georef）

- 使う値: RTK の位置（`GpsStatus` が RTK、`RtkFlag` = 50（固定解）、`RtkStdLon/Lat/Hgt`）、絶対高度（`AbsoluteAltitude`）、LRF の距離と、LRF が当たった地点の標高（`LRFTargetAbsAlt`）、ジンバルの向き（`GimbalYaw/Pitch/RollDegree`）、画素の角度（実測 約 1.01 mrad/画素）
- 計算: ピンホールカメラとして、画像の各画素の視線と「パネル面の高さの水平面」との交点を求める。カメラからパネル面までの高さ = 絶対高度 − パネル面の標高
  - パネル面の標高は、LRF がパネルに当たった画像の `LRFTargetAbsAlt` から架台ごとに推定する（地面に当たった画像の値は地面の標高）。高さの取り違えは画像の端で数十 cm のずれになるため（対地 41 m・画像の中心から 13 m の位置で、高さ 1.5 m の違いは約 0.5 m）
- 真下向き（ジンバルの角度が −90° から設定の範囲内）の画像だけを自動の対象にする。範囲外・RTK が固定解でない・LRF が無い画像は、ずれの見込みが大きいので「位置合わせ不可（要確認）」にする（閾値は設定）
- メタデータの読み取りに `RtkFlag`・`RtkStd*`・`LRFTargetAbsAlt` などを加える（`ImageMetadataExtractor` の `KEPT_TAGS`）
- **実装済み（2026-11-07、手順 2）**: Rails は画像の処理のときに `inspection_images.georef`（撮影情報・使えるか・使えない理由・設定の版）を記録し、点検画面の画像の欄に表示する（`ImageGeoref`、設定は `config/layout_overlay.yml`）。画素と地上の座標の計算は解析エンジンの `analyzer/geo/projection.py`（真下向き・高さ z ごとの縮尺）。検証で分かったこととして、パネル面の標高・上端と下端の高さの差を z で渡す（手順 4・5）。画素の角度はカメラごとの初期値（M4T 0.975 mrad）を設定に置き、架台の地図を作るときに推定し直す

### B-2. 架台の端による補正

撮影情報だけの位置は、2 枚の間で中央値約 0.5 m・最大約 0.8 m ずれた（[spike_dji_sdk.md 6c](spike_dji_sdk.md)）。パネル幅（約 1.3 m）の半分に近いので、パネル単位の割り当てには補正が要る。

1. 画像に入る架台を投影する（予測の位置）
2. 画像の中で架台を検出し、端（長辺・短辺）を画素単位で合わせ込む
3. 投影した架台と検出した架台を対応させる（予測のずれ 0.5 m は架台の長さ約 13 m・列の間の通路より十分小さいので、架台の取り違えは起きにくい）
4. 対応した架台の端・角から、画像全体の補正（平行移動＋小さな回転＋拡大縮小）を最小二乗で求める。拡大縮小はパネル面までの高さの誤差を吸収する
5. 架台の中のパネルの境目の線（パネル内の細い線・架台の間の隙間）も使って、列の位置を確かめる
6. 補正後のずれ（残差）を、画素・m・**パネル幅に対する割合**で記録する

**補正できない・あやしい場合**
- 架台の端（短辺）が 1 つも写っていない画像では、東西方向の位置を境目の線の周期でしか決められない。周期は 1 枚分（約 1.3 m）ずれても同じに見えるので、予測のずれがパネル幅の半分（約 0.65 m）に近いと取り違える。この場合は残差が小さくても「要確認」にする
- 対応した架台が少ない（設定の数未満）・補正量が大きすぎる・残差が閾値を超える → 要確認

### B-3. 位置合わせの結果の記録と、うまく重ならなかった場合

- `inspection_images` に `georef`（使った撮影情報・計算方法・設定の版）と `alignment`（状態・対応した架台・補正量・残差・理由）を追加
- 状態
  - `aligned`: 残差がパネル幅の X 割以内（初期値の案 0.25。設定）→ パネル領域を自動で作り、`panel_grids` に入れる（各要素に `source: "layout"`、架台 ID、各セルのパネル番号を持たせる）。今の解析エンジンは `panel_grids` をそのまま使えるので、検出・分類は変えずに済む
  - `needs_review`（位置合わせ不可）: 画像の解析状態を `needs_review`、理由を「位置合わせ不可」にする。手動グリッドの画面に投影の下書きを出し、人が合わせると人の指定として扱う。人が合わせるまで、その画像の異常は作らない（または作ってもパネル未割り当て）。**正常にはしない**
- パネルごとに「どの画像で解析したか」を記録する（`image_panel_coverages`: 画像・パネル・状態（解析済み／端で切れた／除外／位置合わせ不可）・残差）。C の「N 枚中 M 枚」と、報告書の「未確認のパネル」に使う
- 画像の端で切れたパネルは今までどおり `edge_cut` で除外（他の画像で拾う）

**実装（2026-11-08、手順 5）**: 解析エンジンの `align-layout`（`analyzer/layout/align.py`）と、Rails の `AlignLayoutJob`・`LayoutAlignment`。
- 架台を登録した発電所の、位置合わせに使える画像でグリッドの無いものは、品質チェックの後に位置合わせへ進む（グリッドの自動提案は作らない）。位置合わせに使えない画像は理由を `alignment` に残して手動のグリッドを待つ
- 補正は、予測した架台の辺（上端・下端・始まり・終わり。側も合わせる）と画像の辺の対応から、平行移動・拡大縮小・小さな回転を外れ値を除いて求める。残差（RMS）をパネル幅で割った値が `max_residual_panel_width_ratio`（0.25）以内で、架台の端と長辺の両方の手がかりがあれば自動
- 自動のときはグリッド（`source: layout`・架台の ID）を保存して解析へ。異常は、グリッドの行・列から架台のパネルに割り当て、根拠（位置合わせ（自動）・残差）を `panel_assignment_history` に残す
- 位置合わせできないときは needs_review（`alignment_failed`）。下書きのグリッドを残し、グリッドの画面に表示する。人が直して保存したグリッドは架台の ID を残し（`source: layout_adjusted`）、異常を架台のパネルに割り当てる
- 架台の標高が無いときは、最後に作った架台の地図の候補の推定値（パネル面の標高・上端と下端の差・画素の角度の倍率）を使う
- レビュー画面のパネルの選択肢は、位置合わせのグリッドがある画像では写っている架台のパネルだけにした（数千枚を異常ごとに並べると画面が重いため）。重複のまとめ先の候補は、同じパネル → 同じ架台の順に 50 件まで

### B-4. flight008 の実データでずれを確かめる方法と見込み

正解の配置（図面の座標）が無いので、次の 3 つで確かめる。

1. **補正前のずれ**: 画像から作った架台の地図（A-3）に対し、各画像の検出した架台が補正前にどれだけずれるか。6c の結果から、1 枚あたり 0.3〜0.5 m 程度（パネル幅の 2.5〜4 割）の見込み
2. **補正後のずれ**: 補正後に、投影したパネルの境目と画像の中の境目の線（パネル内の線・架台の間の隙間）の差を測る。架台の端は 1〜2 画素（4〜8 cm）で合わせ込める見込みなので、**補正できた画像ではパネル幅の 1 割以下**の見込み
3. **人の抜き取り確認**: 30 枚程度に投影を重ねた画像を作り、パネル単位で取り違えがないかを数える

合格の目安（案）: 自動の対象にした画像のパネルの 95% 以上で、ずれがパネル幅の 0.25 以内。要確認になる画像の割合も合わせて報告する。

- 必要なデータ: 手順 7 の 41 枚は飛び飛びで、同じ架台が複数の画像に写る組がほとんど無い（試しに投影したところ、2 枚以上で見つかった架台は 2 か所だけ）。地図を作るには、選んだ 339 枚（または一部の範囲の全画像）のサーモを SharePoint から `tmp/spike/` に取り出し、温度に変換する必要がある（読み取りのみ）
- 不確かな点: 試作 2 の架台の検出は、後半の画像（パネル内の線がくっきりしたもの）で取りこぼしが多かった。検出の改良が補正の前提になる。レンズのゆがみ（未補正）が画像の端で効く場合は、複数画像の架台の位置からゆがみの係数を推定する

## C. 異常の重複のまとめ方と、複数画像での確認

### C-1. まとめ方（判定の規則は変えない）

- 新しい単位「地上の異常」（`anomaly_findings`。新規）を作る。今の `anomalies`（画像ごとの検出）は「観測」として残し、`anomaly_finding_id` で束ねる
- まとめる条件: 同じパネル、かつパネル内の位置（パネルの座標系で正規化した位置）が近い（設定。例: パネル幅の 0.2 以内）。種類が違っても同じ場所なら 1 つにまとめ、観測ごとの種類を一覧で見せる
- 複数パネルの異常群（`anomaly_groups`）も、構成パネルの組が同じものをまとめる
- 「N 枚中 M 枚」: N = そのパネルの、その位置を解析できた画像の数（位置合わせ済み・端で切れていない・除外でない）、M = その位置で異常が出た画像の数。両方を `anomaly_findings` に記録し、レビュー画面と報告書に出す
- 代表の観測: 画像の中心に近い（真下に近い）・品質の良い画像の観測を代表にする（表示用。重大度の決め方ではない）
- レビューはまとめた単位で行い、確定・却下は束ねた観測にも入れる（今の異常群のレビューと同じ形）。特定の観測だけ外す操作も用意する
- 件数・アラート・影響容量は、まとめた単位で数える（同じ異常を何枚分も数えない）

**重大度の扱い（ここは決めてほしい点）**: 観測ごとの重大度は今のルールで出る。まとめた異常の重大度を「観測の最大」「代表の観測」「中央値」のどれにするかは判定の規則なので、承認後に決める。決まるまでは観測ごとの重大度を並べて表示し、人がレビューで決める案を推す。

**実装（2026-11-08、承認済みの案 3。簡単な作り）**: 単位は「パネルの候補」（`panel_candidates`。所見（Claude）の findings と名前を分けた）。
- `PanelCandidateBuilder`: パネルが割り当てられ、異常群に属さない異常を束ねる（面状は同じパネルで 1 つ、点状はパネルの中の位置が `point_merge_distance` 以内で 1 つ）。N（解析できた画像の数）・M（異常が出た画像の数）・画像ごとの観測（縦位置・ΔT）・代表の観測（画像の中心に近いもの）を記録。点検の最後の画像の解析が終わったら自動で作り、画面の「作り直す」でもやり直せる。人が判断した候補は作り直さない
- 目印（判定は変えない）: 1 枚だけ・写る位置で変わる・多くの架台の同じ位置。条件は `config/panel_candidates.yml`
- 画面（点検 → 「パネルごとの候補を確認する」）: パネルごとに 1 行、写った全画像の切り出し（異常が出た画像は赤枠）、目印で絞り込み、1 件ずつ確定・却下、選んだ候補をまとめて却下（理由に「部材・構造物」など）。確定は代表の観測を確定し、ほかの画像の観測は代表への重複として却下（学習データでは異常ありになる）。種類・位置の修正は画像ごとのレビュー画面
- 異常群（隣接パネル群）は今までどおり画像ごとのレビュー画面で判断する
- 重大度の決め方（C-1 の決めてほしい点）と証拠レベルへの反映（C-3）は 11 月の案件の後に決める（ユーザー指示）

### C-1b. 架台・段の候補（案 X 改。2026-11-08 ユーザー承認・実装）

基準温度を画像内の位置の傾向から取る方法（2026-11-trend-provisional）は、架台全体のような広い発熱を傾向に取り込んで見落とすことがある（既知の問題 X）。それを補うため、点検の最後に架台の段ごとの温度を比べる。
- 計算（`BlockRowEffect`）: 点検の解析結果のパネル（端で切れていないもの）の平均温度から画像ごとの中央値を引き、見え方の影響を画像内の位置の 2 次式 f(縦, 横) として全画像から 1 つだけ求める（外れ値を除いて当てはめ直す）。段の効果 = その段が写った画像ごとの残りの差の平均の、画像をまたいだ中央値。画像ごとに関数を求めないので、1 つの架台が熱くても吸収されない。SDK は呼び直さない
- 閾値: ルールセットの `block_row`（measure `row_effect`。無くてもよい種類で、無い版では候補を作らない）。`2026-11-trend-row-provisional` は 候補 +0.8℃（飛行 008 の 1 回分から決めた暫定値。次の点検データで見直す）・注意 +1.5℃・重大 +3.0℃（依頼元と合意するまでの仮の値）。段ごとに判定に使った版と閾値を残す
- 判断できる条件（`config/row_effect.yml`）: 3 枚以上の画像に写り、画像の上半分（縦 0.45 未満）にも下半分（縦 0.55 超）にも写ること。満たさない段は「判断の材料が足りない」（理由つき。正常にはしない）。見え方の影響の関数は、解析済み 40 枚以上で、パネルが画像の上から下まで写っているときだけ求める（足りなければ全段が判断の材料が足りない）
- 画面: パネルごとの候補の上に「架台・段の候補」。配置図に段ごとの効果を色で示し、候補（段の全画像の切り出し）を確定・却下、判断の材料が足りない段を理由つきで一覧。確定した段の重大度は点検の重要度に入り、未判断の段はレビュー完了のときの未確定の候補に数える
- 本番では有効にしない（業者の報告書・次の点検データと比べてから。ユーザー指示）

### C-1c. 発電所ごとの部材の位置（案 A。2026-11-08 ユーザー承認・実装）

架台の端の金具など、パネルの故障ではない部材は、次の点検でも同じ位置に出る。
- 登録: パネルごとの候補を「部材・構造物」でまとめて却下するとき、「この位置を部材の位置として登録する」を選ぶと、点状の発熱の候補の位置（段・列・パネルの中の区画。区画の数は `config/panel_candidates.yml` の `same_position_grid_bins`）を発電所に登録する（`structure_positions`）。すべての架台に共通の位置として扱う
- 次の点検から: 登録した位置に出た点状の発熱の候補に「登録済みの部材の位置」の目印を付け、一覧ではたたんで表示する（目印で絞り込むと表示し、まとめて判断できる）。**自動では却下せず、検出も変えない**
- 一覧・削除: 発電所一覧の「部材の位置」

### C-2. 複数画像での確認（反射の除外）

- 反射（太陽の映り込み）は見る位置で動き、本物の発熱はパネルに対して動かない。M/N が小さい（例: 5 枚中 1 枚だけ）のは反射の疑いが強い
- **規則を変えない範囲でできること**: M/N を記録して表示し、M = 1 かつ N ≥ 3 のものに `transient_suspect`（1 枚だけで高温）の目印を付けてレビューで目立たせる。自動で却下・正常にはしない
- 真下向きの撮影で、パネルの傾斜角を β とすると、カメラには南の天頂角 2β の方向の空が映る。太陽がその方向にあると反射が出る（例: 傾斜 30° なら、南の高度 30° 付近の太陽。11 月中旬の正午の太陽高度は北緯 35° で約 36°、北緯 45° で約 26° なので、傾斜の大きい発電所を真下向きで撮ると、正午付近に反射が出やすい可能性がある）。撮影時刻の検討に使う（E）

### C-3. 証拠レベルへの反映（判定の規則の変更。別の案として）

今の証拠レベル（A: 電気測定あり、B/C）に、複数画像での再現性を加える案。**承認が無い限り実装しない。**

- 案 1（推奨）: 「N ≥ 3 かつ M/N ≥ 2/3」を B の条件の 1 つに加える。「N ≥ 3 かつ M = 1」は C のまま、反射の疑いを明記する。N < 3（再現性を確かめられない）は今のまま
- 案 2: 再現性を証拠レベルとは別の項目（「再現性: 5 枚中 4 枚」）として報告書に載せ、証拠レベルは変えない
- どちらも、反射の疑いで重大度を下げたり正常にしたりはしない

## D. 解析する画像の選び方

- **推奨: 各パネルが丸ごと写る画像が 3 枚以上になるように選んで解析する**（M/N のため）。flight008 の飛び方（ライン間隔 約 6.7 m・撮影間隔 約 3.5 m・1 枚 約 27 m × 21 m）では、ライン 1 本おき・撮影 1 枚おき（約 4 分の 1、約 480 枚）で、各パネルが 4〜5 枚に丸ごと写る見込み
- 架台の地図を作るとき（発電所の 1 回目）は、同じ選び方の画像で足りる見込み（架台が丸ごと写る画像が架台ごとに数枚ある）
- 全枚数（約 1,900 枚）の解析も仕組みとしては可能（位置合わせは自動のため）。ただし、原本の保存容量（RGB を含めると 1 回の飛行で数 GB〜10 GB）・ブラウザからの登録の手間・解析時間が増える。解析時間は本番の計算機で測ってから決める
- 選び方は `analyzer/scripts/select_images.py` の間隔の設定で変えられる。将来は「各パネルが N 枚以上に写るか」を配置から直接数えて選ぶ（重なり具合の確認にも使う）

## E. 撮影手順の案

この方式がうまく動く撮り方（案。規格の値は原文で確認するまで目安として扱う）。

| 項目 | 案 | 理由 |
|---|---|---|
| カメラの向き | 真下（ジンバル −90°）、機首・ジンバルの向きを飛行中ずっと固定（例: 北が上） | 位置の変換が単純で、ずれが小さい。向きが変わる折り返しの画像は使わない |
| ルート | 自動飛行。飛行ラインを架台の長辺と平行にする | 架台の端が画像に入りやすく、補正しやすい |
| 重なり | 進行方向 75〜80%、横（隣の飛行ラインとの重なり）は**画像の縦の幅の半分以上**。**各パネルが丸ごと写る画像が 3 枚以上**になること | 反射の除外（M/N）と、端で切れたパネルを他の画像で拾うため。横の重なりは、各段が画像の上側にも下側にも写り、架台・段の候補で判断できるようにするため（2026-11-08 追記） |
| 高度 | 下の式で「1 セル 5×5 画素以上」になる高度（パネル面から） | 解像度の目安 |
| RTK | 固定解（`RtkFlag` 50）を確認してから撮影 | 位置の変換の前提 |
| LRF | 有効にする | パネル面の高さと距離の補正 |
| 速度 | 4 m/s 程度以下（ぶれが出たら下げる） | サーモはぶれやすい |
| 撮影時間帯 | 日射が強く安定している時間。太陽が「南の天頂角 2β」の方向（C-2）に近い時間は避ける | 日射の目安と反射 |
| 日射量 | モジュール面（POA）の日射計を設置し、時刻付きで 1 分以内の間隔で記録。アプリの気象データに入れる | ΔT の正規化に POA が要る |
| 記録 | 雲量・風速・気温、機材・高度・重なりの設定 | 報告書の撮影条件 |

**反射の確認**: 撮影前に `analyzer/scripts/glare_check.py`（2026-11-07 追加。使い方は analyzer/README.md）で、撮影日・時間帯に反射が写るか、カメラを傾ける案で避けられるかを計算する。

**1 セル 5×5 画素以上を確保できる高度**（M4T のサーモ、画素の角度 約 1.01 mrad で計算）

パネル面からの高さ H ≤ セルの寸法 ×（傾斜の方向は cos β）÷（5 × 0.00101）

| セルの寸法（パネルの寸法を要確認） | 水平な方向 | 傾斜 30° の方向 |
|---|---|---|
| 210 mm（G12 系のセルの一辺） | 41 m 以下 | 36 m 以下 |
| 182 mm（M10 系） | 36 m 以下 | 31 m 以下 |
| 105 mm（G12 ハーフカットの短辺） | 21 m 以下 | 18 m 以下 |
| 91 mm（M10 ハーフカットの短辺） | 18 m 以下 | 15 m 以下 |

- ハーフカットのセルを「半分のセル」で数えるか「元のセル」で数えるかで高度が大きく変わる。規格の原文で確認してから決める（今の手順書の「撮影条件の目安」と同じ扱い）
- 1 割ほど余裕を見て決める。高度を下げると 1 枚の範囲が狭くなり（30 m で約 19 m × 16 m）、枚数と飛行時間が増える
- 架台の大きさ（約 13 m × 5 m）に対し、1 枚に架台の端が少なくとも 1 つ入る範囲を保つ（補正のため）

## F. Mac の開発環境で、解析エンジンを Docker（linux/amd64）の中で動かす

DJI Thermal SDK は linux/amd64 専用のため、Mac（Apple Silicon）では Docker の中で動かす。

- **方法（推奨）**: 解析エンジンの起動コマンドを設定で差し替える仕組みが既にある（`config/analyzer.yml` の `command`）。開発用のコマンドとして `bin/analyzer-docker` を用意し、中で `docker exec -i <コンテナ> /opt/venv/bin/python -m analyzer "$@"` を呼ぶ
- **ファイルの受け渡し**: Rails は一時ファイルのパスを解析エンジンに渡す。コンテナには**プロジェクトのディレクトリを同じパスでマウント**し、解析用の一時ファイルをプロジェクトの `tmp/analyzer/` に作るようにする（`config/analyzer.yml` に `work_dir` を追加。本番・テストは今のまま）。これでパスの読み替えが要らない
- **コンテナの用意**: `bin/analyzer-container up`（python:3.12-slim・linux/amd64・`libgomp1`・`uv sync`、SDK を読み取り専用でマウント、`DJI_IRP_PATH` を設定）。今の検証用コンテナ（`tsdk-spike`）の手順を元にする。SDK はコミットしない
- **開発用の設定**: `.env`（コミットしない）の `ANALYZER_COMMAND=bin/analyzer-docker` などで切り替え、未設定なら今のまま（Mac の uv、.npy の合成データだけ）
- エミュレーションで動くので遅い。速度は本番の目安にしない
- 確かめること: 画面から実画像（R-JPEG）を登録 → 品質チェック → 位置合わせ → 解析 → レビュー画面まで通る
- **実装済み（2026-11-07）**: `bin/analyzer-container up|status|down`（コンテナ名 `solarsight-analyzer`）、`bin/analyzer-docker`、`config/analyzer.yml` の `work_dir` と、development で `ANALYZER_DOCKER=1` のときの切り替え。点検画面の「再解析」から、実画像がコンテナの中の SDK で解析されることを確認した（位置合わせは手順 2〜5 で追加）

- 0〜5 で 7.5〜8 日。11 月半ばまでの作業日を 7〜8 日と見ると、**最小構成（重複のまとめ無し）がぎりぎり**。0 の検証で架台の検出がうまくいかなければ間に合わない
- 11 月半ばまでの最小構成では、架台の地図の確認は「投影を重ねた画像（PNG）を見て、架台の CSV を直して取り込み直す」形にする（6 の確認画面の代わり）

### G-2. 11 月の案件での進め方（3 つの場合）

| 場合 | 進め方 | 人の作業時間の見込み |
|---|---|---|
| 最小構成が間に合った | 架台の地図を PNG と CSV で確認（1 回）→ 自動の位置合わせ → 要確認の画像だけ手動グリッド → 画像ごとの異常をレビュー（同じパネル番号の異常が並ぶので、重複は人が見て却下） | 地図の確認 1〜2 時間 ＋ 手動グリッド（要確認が 2 割なら約 70 枚 × 架台 4 つ × 30 秒 ≒ 2〜3 時間）＋ レビュー |
| 位置合わせが間に合わない | 今の代わりの手順（約 340 枚・架台ごとに 1 回グリッドを指定） | 約 340 枚 × 架台 3〜5 つ × 20〜40 秒 ≒ **7〜19 時間**（中央 約 11 時間）＋ レビュー |
| 一部の画像だけ位置合わせできた | 位置合わせできた画像は自動、残りは手動 | 上の 2 つの間 |

- 重複のまとめが無い間は、同じ異常が複数の画像で候補に出る。レビューで「他の画像と重複」として却下する理由が要る（今の却下の理由は グレア・影・汚れ・その他）。**却下の理由を 1 つ加えるかは確認したい点**（加えない場合は「その他」＋メモ）
- 手動グリッドの 1 グリッドあたりの時間は計測していない（中止したため）。上の時間は 20〜40 秒の仮定

### G-3. 先に決めてほしいこと

1. この方向（画像から架台の地図を作り、人は発電所ごとに 1 回確認）で進めてよいか。図面の座標がある発電所は図面から登録する
2. 0 の検証のために、選んだ 339 枚のサーモを SharePoint から `tmp/spike/` に取り出してよいか（読み取りのみ。約 0.5 GB）
3. 位置合わせの閾値の初期値（残差がパネル幅の 0.25 以内で自動）
4. まとめた異常の重大度の決め方（C-1）と、証拠レベルへの反映の案（C-3）は 11 月の案件の後に決める、でよいか
5. 却下の理由に「他の画像と重複」を加えるか
6. 11 月の案件の撮影は、これから撮るのか（E の撮影手順を使えるか）、既に撮ったデータか

## 付録: 主なリスク

| リスク | 影響 | 対策 |
|---|---|---|
| 架台の検出がパネル内の線のくっきりした画像で取りこぼす | 補正できない画像が増える | 0 の検証で改良。だめなら境目の線の周期を併用し、あやしいものは要確認 |
| パネル面の高さ・傾斜による投影のずれ | 画像の端でずれが大きくなる | パネル面の標高を LRF から推定。補正で拡大縮小を求める |

| 真下向きでの反射 | 偽の候補 | M/N の記録、撮影時間帯の選び方（E） |
